File Path Traversal

Simple Case

Laboratorio práctico enfocado en el análisis de una vulnerabilidad de File Path Traversal o Directory Traversal en una aplicación web.

Información del laboratorio

Nombre del laboratorio: File Path Traversal, Simple Case

Nivel: Apprentice

Tipo de explotación: File Path Traversal

Plataforma: PortSwigger Web Security Academy

Herramienta utilizada: Burp Suite

Laboratorio: File path traversal, simple case

Marco teórico

La vulnerabilidad de File Path Traversal o Directory Traversal ocurre cuando una aplicación web utiliza entradas proporcionadas por el usuario de forma insegura para construir rutas del sistema de archivos, sin realizar una validación o sanitización adecuada.

Su funcionamiento se basa en insertar secuencias de navegación de directorios, como en sistemas Linux o en sistemas Windows, con el objetivo de retroceder desde el directorio establecido por la aplicación y acceder a recursos fuera de la ubicación permitida.

Impacto en la tríada CIA

Confidencialidad: el impacto puede ser alto, ya que una vulnerabilidad de este tipo puede permitir la lectura no autorizada de código fuente, archivos de configuración, credenciales y otros datos sensibles del sistema.

Integridad y disponibilidad: el impacto es menor cuando la vulnerabilidad solamente permite lectura de archivos, pero el riesgo puede aumentar si se combina con vulnerabilidades que permitan escritura arbitraria o el compromiso de credenciales.

Relación con OWASP

En el contexto de OWASP Top 10:2025, el documento relaciona esta vulnerabilidad con A01:2025 - Broken Access Control . OWASP mantiene esta categoría como una de las principales áreas de riesgo para aplicaciones web y contempla, entre sus debilidades relacionadas, distintos casos de Path Traversal.

1. Objetivo del laboratorio

El objetivo del laboratorio es recuperar y visualizar el contenido del archivo /etc/passwd del servidor mediante la vulnerabilidad de File Path Traversal.

2. Vulnerabilidad identificada

La aplicación procesa la solicitud de imágenes mediante un parámetro denominado filename.

El backend utiliza directamente este valor para resolver el recurso dentro del sistema de archivos sin restringir correctamente que la búsqueda permanezca dentro del directorio permitido.

En el escenario documentado se considera como directorio esperado: 

/var/www/images/

La falta de validación adecuada permite manipular el parámetro y solicitar una ruta diferente a la prevista por la aplicación.

3. Procedimiento

  1. Abrir el laboratorio File Path Traversal, Simple Case en PortSwigger Web Security Academy.
  2. Interceptar mediante Burp Suite una solicitud HTTP asociada con la carga de una imagen.
  3. Localizar el parámetro filename dentro de la petición.
  4. Enviar la petición al módulo Repeater mediante la opción Send to Repeater .
  5. Analizar la petición y modificar el valor del parámetro vulnerable dentro del laboratorio.
  6. Enviar nuevamente la petición y revisar la respuesta generada por el servidor.
  7. Comprobar que el contenido solicitado fue devuelto y verificar el estado de Lab Solved .

4. Payload utilizado

Para el laboratorio se utilizó el siguiente valor en el parámetro vulnerable: 

../../../etc/passwd

Explicación

La secuencia se utiliza para retroceder un nivel dentro de la estructura de directorios.

En el escenario planteado:

  • El primer retrocede desde /var/www/app/resources/ hacia /var/www/app/.
  • El siguiente continúa ascendiendo en la estructura de directorios.
  • El tercer permite alcanzar una ubicación superior desde la cual se solicita el recurso /etc/passwd.

La parte etc/passwd especifica el recurso que se desea solicitar dentro del sistema de archivos.

El problema se produce porque la aplicación no valida adecuadamente los caracteres utilizados para la navegación de directorios antes de resolver la ruta.

5. Resultado de la explotación

Después de modificar la solicitud y enviarla nuevamente, la aplicación devuelve el contenido del archivo solicitado.

La obtención del archivo /etc/passwd confirma que la aplicación no está restringiendo correctamente la ruta proporcionada mediante el parámetro vulnerable.

La evidencia visual del resultado se incorporará en esta sección.

6. Confirmación del laboratorio

Una vez realizada correctamente la prueba, PortSwigger muestra el estado Lab Solved , confirmando que el objetivo del laboratorio fue completado.

7. Mitigación recomendada

Para prevenir vulnerabilidades de File Path Traversal se deben implementar controles que impidan que las entradas del usuario sean utilizadas directamente como rutas del sistema de archivos.

Evitar la entrada directa

No utilizar directamente nombres de archivos o rutas proporcionadas por el usuario en las APIs del sistema de archivos.

Una alternativa consiste en utilizar identificadores numéricos o claves asociadas a recursos almacenados en una base de datos.

Validación

La entrada recibida debe validarse antes de ser procesada, evitando secuencias que permitan abandonar el directorio autorizado.

Verificación de ruta

La aplicación debe comprobar que la ruta final permanezca dentro del directorio permitido después de su normalización.

También se recomienda aplicar el principio de mínimo privilegio para limitar el impacto en caso de que una aplicación llegue a presentar una vulnerabilidad de este tipo.

8. Conclusión

Este laboratorio permitió comprender de manera práctica cómo una aplicación web puede exponer archivos del sistema cuando utiliza rutas proporcionadas por el usuario sin realizar una validación adecuada.

Mediante la modificación controlada de una solicitud HTTP fue posible comprobar el comportamiento de la aplicación frente a una entrada de tipo Path Traversal y observar el acceso al archivo /etc/passwd.

La actividad también permitió reforzar la importancia de validar las rutas, aplicar el principio de mínimo privilegio y evitar que las entradas del usuario controlen directamente el acceso al sistema de archivos.

ROAD TO HALL OF FAME · LAB 05

File Path Traversal: Validation of Start of Path

Actividad 11 del portafolio. Laboratorio enfocado en el análisis de una validación basada en el inicio de una ruta y en cómo una comprobación incompleta puede ser evadida mediante secuencias de traversal.

Nivel
Practitioner
Tipo
Path Traversal · Start Path Bypass
Herramienta
Burp Suite
Plataforma
PortSwigger Web Security Academy

01 · Marco teórico

Las aplicaciones web que gestionan recursos estáticos pueden aplicar validaciones basadas en prefijos para comprobar que los archivos solicitados pertenezcan exclusivamente a un directorio autorizado.

Sin embargo, si la validación se limita únicamente a comprobar el inicio de la cadena sin realizar una normalización o canonicalización posterior de la ruta completa, una entrada puede contener posteriormente secuencias de escape de directorios.

Esta diferencia entre la validación textual inicial y la interpretación final de la ruta puede generar una vulnerabilidad de File Path Traversal.

02 · Objetivo

Demostrar y documentar la explotación de una vulnerabilidad de Path Traversal protegida mediante una validación defectuosa del inicio de la ruta.

Para ello se emplea Burp Suite con el propósito de interceptar y modificar una petición HTTP, comprobando cómo un prefijo aparentemente válido puede ser seguido por secuencias de traversal.

03 · Vulnerabilidad

Nombre: File Path Traversal — Validation of Start of Path.

La aplicación comprueba que el valor proporcionado comience con un directorio permitido. El problema aparece cuando esta comprobación solamente analiza el prefijo textual y no verifica la ruta completa una vez normalizada.

Como consecuencia, una ruta puede comenzar con el prefijo esperado y posteriormente incorporar secuencias de desplazamiento de directorio.

04 · Procedimiento paso a paso

  • 4.1 Configuración del entorno: Se configuró Burp Suite como proxy de intercepción para capturar el tráfico HTTP generado por el navegador utilizado para acceder al laboratorio.
  • 4.2 Generación de la petición base: Se navegó por la aplicación del laboratorio y se seleccionó un producto para generar una solicitud destinada a cargar una imagen.
  • 4.3 Captura de la solicitud: La petición fue localizada dentro del historial HTTP de Burp Suite, identificando el parámetro filename.
  • 4.4 Envío a Repeater: La solicitud fue enviada a Repeater para realizar modificaciones controladas sobre el parámetro.
  • 4.5 Inclusión del prefijo válido: El parámetro fue modificado para comenzar con el directorio permitido por la aplicación y posteriormente incluir secuencias de traversal.
  • 4.6 Envío y análisis: Se envió la petición modificada y se examinó la respuesta HTTP generada por el servidor.
  • 4.7 Confirmación: Finalmente se verificó la respuesta del laboratorio y la notificación correspondiente de resolución.

05 · Petición base

La aplicación utiliza el parámetro filename para determinar el recurso gráfico que debe cargar.

GET /image?filename=14.jpg HTTP/1.1

Esta petición fue utilizada como punto de partida para analizar la validación aplicada por el servidor.

06 · Payload utilizado

El payload documentado para la actividad utiliza el prefijo de ruta autorizado seguido por las secuencias de desplazamiento:

GET /image?filename=/var/www/images/../../../../etc/passwd HTTP/1.1
`/var/www/images/`

Corresponde al prefijo de ruta que la validación espera encontrar al inicio del parámetro.

`../`

Representa el desplazamiento hacia directorios superiores durante la resolución de la ruta.

`/etc/passwd`

Archivo utilizado en el laboratorio para comprobar el acceso a un recurso ubicado fuera del directorio previsto.

07 · Explicación técnica del payload

La rutina de validación comprueba inicialmente que el parámetro comience con una ruta considerada válida, como:

/var/www/images/

El problema se produce porque esta comprobación se realiza sobre el comienzo de la cadena y no sobre la ruta final después de su normalización.

Una vez superada la validación inicial, las secuencias ../ pueden ser interpretadas durante la resolución de la ruta, provocando que el sistema retroceda niveles de directorio.

Concepto clave: validar únicamente el prefijo textual de una ruta no garantiza que la ruta resultante se encuentre realmente dentro del directorio autorizado.

08 · Resultado esperado

Después de enviar la solicitud modificada, el servidor procesa la ruta proporcionada después de la validación inicial.

En el laboratorio exitoso, la resolución de las secuencias de traversal permite acceder al recurso utilizado como objetivo de comprobación.

Evidencia de éxito: La comprobación final corresponde a la respuesta obtenida en Burp Suite y a la notificación de laboratorio resuelto proporcionada por PortSwigger.

09 · Impacto

Una vulnerabilidad de Path Traversal puede permitir el acceso a archivos ubicados fuera del directorio que la aplicación pretendía exponer.

Dependiendo de los permisos del proceso y de los recursos disponibles en el servidor, esta vulnerabilidad puede provocar exposición de información sensible.

El impacto puede incluir archivos internos, información de configuración y otros recursos que no deberían estar disponibles a través del parámetro controlado por el usuario.

10 · Mitigación

  • Validación integral: No depender únicamente de una comprobación textual del comienzo de una ruta.
  • Canonicalización: Resolver la ruta absoluta real antes de determinar si pertenece al directorio autorizado.
  • Comparación segura: Comprobar que la ruta final permanezca realmente dentro del directorio base permitido.
  • Restricción de recursos: Cuando sea posible, utilizar identificadores de archivos permitidos en lugar de permitir rutas arbitrarias proporcionadas por el usuario.
  • Mínimo privilegio: El proceso de la aplicación debe contar únicamente con los permisos necesarios para acceder a sus propios recursos.

12 · Conclusión

La actividad permitió comprobar que una validación basada únicamente en el inicio textual de una ruta puede resultar insuficiente para proteger una aplicación contra Path Traversal.

La práctica demuestra la importancia de realizar una validación completa sobre la ruta normalizada y no únicamente sobre una parte de la cadena proporcionada por el usuario.

La utilización de mecanismos de canonicalización y la aplicación del principio de mínimo privilegio son elementos fundamentales para reducir el riesgo asociado con este tipo de vulnerabilidad.

ROAD TO HALL OF FAME · LAB 04

File Path Traversal: Traversal Sequences Stripped with Superfluous URL-Decode

Actividad 10 del portafolio. Laboratorio enfocado en el análisis de una vulnerabilidad de File Path Traversal donde un proceso de decodificación URL superfluo permite evadir un mecanismo de filtrado mediante una secuencia codificada.

Nivel
Practitioner
Tipo
Path Traversal · URL Decode Bypass
Herramienta
Burp Suite
Plataforma
PortSwigger Web Security Academy

01 · Marco teórico

La seguridad en las aplicaciones web depende de una correcta validación y normalización de las entradas proporcionadas por los usuarios. Cuando una aplicación utiliza filtros de saneamiento para eliminar secuencias asociadas con Path Traversal, la implementación debe considerar cuidadosamente el orden en que se realizan las operaciones de decodificación y validación.

Un problema puede aparecer cuando el sistema realiza una decodificación URL adicional después de que el filtro ya haya evaluado la entrada. En este escenario, una secuencia que inicialmente no coincide con el patrón bloqueado puede transformarse posteriormente en una secuencia interpretable por el sistema de archivos.

Este tipo de comportamiento puede permitir que un atacante manipule parámetros utilizados para construir rutas y acceda a archivos fuera del directorio previsto por la aplicación.

02 · Objetivo

Demostrar y documentar la explotación de una vulnerabilidad de File Path Traversal protegida por un filtro que realiza una decodificación URL superflua, utilizando Burp Suite para interceptar, modificar y analizar las peticiones HTTP.

El objetivo práctico es comprobar cómo una secuencia de traversal codificada puede superar el filtro inicial y ser posteriormente interpretada por la aplicación.

03 · Vulnerabilidad

Nombre: File Path Traversal — Traversal Sequences Stripped with Superfluous URL-Decode.

La vulnerabilidad aparece cuando la aplicación intenta eliminar secuencias de traversal antes de realizar otra operación de decodificación. La entrada puede ser interpretada de manera diferente durante las distintas etapas del procesamiento.

El resultado es una discrepancia entre lo que analiza el filtro y lo que finalmente interpreta el componente encargado de procesar la ruta.

04 · Procedimiento paso a paso

  • 4.1 Configuración del entorno: Se inició el laboratorio de PortSwigger y se utilizó Burp Suite como proxy de intercepción para observar el tráfico HTTP generado por la aplicación.
  • 4.2 Generación de la petición base: Se navegó por la tienda virtual y se seleccionó un producto para generar la petición correspondiente a la carga de una imagen.
  • 4.3 Captura de la solicitud: En Burp Suite se localizó la petición relacionada con la carga de la imagen, observando el parámetro filename.
  • 4.4 Envío a Repeater: La petición fue enviada al módulo Repeater para permitir la modificación controlada del parámetro y observar las respuestas del servidor.
  • 4.5 Aplicación del bypass: Se sustituyeron las secuencias normales de traversal por una representación con codificación URL superflua.
  • 4.6 Validación: Se envió la petición modificada y se analizó la respuesta HTTP para determinar si la aplicación había procesado la ruta resultante.
  • 4.7 Confirmación del laboratorio: Una vez que la explotación fue aceptada por el laboratorio, se verificó la notificación de éxito proporcionada por la plataforma.

05 · Petición base

La aplicación utiliza un parámetro de nombre filename para determinar el recurso que debe cargar. Una petición representativa utilizada durante el análisis es:

GET /image?filename=14.jpg HTTP/1.1

Esta solicitud constituye el punto de partida para analizar cómo la aplicación procesa el parámetro antes de acceder al recurso solicitado.

06 · Payload utilizado

Para realizar el bypass se utilizó una representación con codificación URL superflua:

GET /image?filename=..%252f..%252f..%252fetc/passwd HTTP/1.1

El valor del parámetro filename contiene una representación codificada de las secuencias necesarias para construir el traversal.

`..`

Representa el componente utilizado para desplazarse al directorio padre.

`%252f`

Representa una codificación URL superflua del separador `/`. Durante el procesamiento puede transformarse mediante una segunda decodificación.

`/etc/passwd`

Archivo del sistema utilizado como objetivo de lectura en el laboratorio para comprobar el acceso fuera del directorio previsto.

07 · Explicación técnica del payload

El funcionamiento del bypass depende del orden en que la aplicación realiza el filtrado y la decodificación.

Una representación como %252f contiene una codificación adicional del carácter utilizado como separador de ruta. Por ello, una primera etapa de procesamiento puede no interpretarlo directamente como /.

Si posteriormente la aplicación realiza otra decodificación URL, el valor puede transformarse y recuperar el carácter que representa el separador de directorios.

Concepto clave: el filtro y el componente que utiliza finalmente la ruta pueden estar trabajando con representaciones diferentes de la misma entrada. Esta diferencia de interpretación es la base del bypass.

08 · Resultado esperado

Después de enviar la petición modificada, se analiza la respuesta proporcionada por el servidor.

En el laboratorio exitoso, la aplicación procesa la ruta resultante y permite recuperar el contenido del archivo objetivo utilizado para la comprobación.

09 · Impacto

Una vulnerabilidad de Path Traversal puede permitir que una aplicación acceda a recursos ubicados fuera del directorio previsto.

Dependiendo de los permisos disponibles y de la arquitectura de la aplicación, esto puede comprometer información sensible almacenada en el servidor.

Entre los posibles impactos se encuentran la exposición de información de configuración, credenciales almacenadas de manera insegura, archivos internos y otros recursos accesibles mediante el sistema de archivos.

10 · Mitigación

  • Validación estricta de entradas: Los valores proporcionados por el usuario deben validarse mediante reglas estrictas antes de ser utilizados para construir rutas.
  • Canonicalización: La aplicación debe normalizar la ruta antes de comprobar si se encuentra dentro del directorio autorizado.
  • Evitar decodificaciones redundantes: No deben realizarse múltiples procesos de URL-decode que cambien el significado de la entrada después de haber sido validada.
  • Uso de rutas permitidas: Siempre que sea posible, deben utilizarse identificadores o listas de recursos permitidos en lugar de aceptar rutas arbitrarias proporcionadas por el usuario.
  • Principio de mínimo privilegio: El proceso de la aplicación debe disponer únicamente de los permisos necesarios para acceder a sus recursos.

12 · Conclusión

La actividad permitió comprobar cómo una implementación incorrecta del procesamiento de entradas puede generar una vulnerabilidad de File Path Traversal.

El uso de una codificación URL superflua demuestra que un filtro puede interpretar una entrada de manera diferente a la aplicación que posteriormente procesa la ruta.

Por esta razón, las aplicaciones web deben realizar la normalización y validación de las entradas de manera consistente, evitando transformaciones posteriores que modifiquen el significado de datos que ya fueron validados.
